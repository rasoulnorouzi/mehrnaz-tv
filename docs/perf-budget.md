# Performance budget & how to measure it

Target hardware: Mi TV P1 43": 4× Cortex-A55 @1.5 GHz, Mali-G52 MP2, **2 GB RAM**, Android 10 (API 29).
All numbers are measured on **the real TV**, release build, with the Baseline Profile installed.
The emulator is for screenshots and profile generation only; never quote emulator timings.
(Proof, 2026-10-11: the API 29 TV emulator renders in software, so a trivial screen showed 90 % janky frames
and `Graphics: 0 KB`. Emulator frame stats are meaningless; `tools/tv.sh perf` flags them.)

## Budgets
| Metric | Budget | How it's measured |
|---|---|---|
| Cold start → home rows visible (from cache) | **≤ 1.5 s** | Macrobenchmark `StartupTimingMetric` (TTID) / `am start -W` |
| Warm start | ≤ 0.5 s | `am start -W` |
| Home D-pad scrolling (rows + across rows) | p90 frame CPU ≤ 16 ms, janky frames < 5 % | Macrobenchmark `FrameTimingMetric` (`frameDurationCpuMs`), `dumpsys gfxinfo` |
| Open details (cached / network) | ≤ 0.4 s / ≤ 1.0 s | custom trace section `details_ready` |
| **Time to first video frame** (Play pressed → first frame) | ≤ 2.0 s at 720p on home Wi-Fi | `onRenderedFirstFrame` − play click (logged + overlay) |
| Resume/seek → frame | ≤ 1.0 s | PlaybackStats mean seek time |
| Rebuffers in a 10-min 720p session | 0 | PlaybackStats |
| Dropped video frames | ≈ 0 / min at 1080p | PlaybackStats / `EventLogger` |
| Memory while browsing | total PSS ≤ 180 MB, image memory ≤ 40 MB | `dumpsys meminfo <pkg>` |
| Memory while playing | total PSS ≤ 250 MB, buffer ≤ 60 MB | `dumpsys meminfo`, LoadControl caps |
| APK size (release) | ≤ 15 MB | `ls -l app-release.apk` |
| Main-thread disk/network I/O | 0 | StrictMode in debug builds |

The **official app's numbers** for the same metrics are recorded in M0.6 (`perf/reports/official-baseline.md`).
Our app must beat them on every row.

## How the user can see performance
1. **On the TV (live):** a hidden **debug overlay** (Settings → Developer → "Show performance",
   or press MENU 3× on the home screen). It shows FPS + janky-frame %, Java/native memory,
   and during playback: resolution, bitrate, buffered seconds, dropped frames, and TTFF of the current video.
2. **On the desktop (live):** `scrcpy` mirrors the TV screen to your computer, so you can watch
   while Claude drives it with `tools/tv.sh key …`.
3. **Reports:** `tools/tv.sh perf` runs a standard scenario (cold start ×5, scroll home, open details,
   play 60 s) and writes `perf/reports/<date>-<git-sha>.md`: a table of measured value vs budget vs
   official app, with ✅/❌ per row.
4. **Trend dashboard:** `perf/dashboard.html` is regenerated after each report from all reports
   (charts of startup, jank, TTFF, memory over versions). Open it in a browser.
5. **Deep dives (Claude or you):** Perfetto traces (`tools/tv.sh trace 10s` → open in ui.perfetto.dev),
   Android Studio Profiler over Wi-Fi ADB, LeakCanary notifications in debug builds.

## Measurement commands (wrapped by tools/tv.sh)
```bash
adb connect $TV_IP:5555
adb shell am force-stop $PKG && adb shell am start -W -n $PKG/.MainActivity      # TotalTime
adb shell dumpsys gfxinfo $PKG reset; <drive scroll>; adb shell dumpsys gfxinfo $PKG   # jank %
adb shell dumpsys meminfo $PKG                                                       # PSS
adb exec-out screencap -p > shot.png                                                 # screenshot
adb shell input keyevent KEYCODE_DPAD_RIGHT                                          # remote keys
adb shell setprop persist.traced.enable 1   # once, Android 10, before Perfetto
tools/gw.sh :benchmark:connectedBenchmarkAndroidTest                                 # Macrobenchmark (see §How to run)
```

## Android 10 limitations (know these)
- Macrobenchmark: `timeToFullDisplayMs` may be missing; `frameOverrunMs` needs API 31+. Use `frameDurationCpuMs`.
- **Baseline Profiles can't be generated on this TV** (needs root or API 33+). Generate them on the
  Android TV API 34 emulator, ship them in the APK, and verify the gain on the TV with Macrobenchmark
  (`CompilationMode.None` vs `Partial`).
- Perfetto on API 29: set `persist.traced.enable 1` and pass the config via stdin.

## How to run: Baseline Profile and Macrobenchmark (M1.8, M4.1)
Two instrumentation-only modules drive the app through the same four D-pad journeys. They are RTL-aware
(LEFT = forward along a row) and live in one shared source set, `baselineprofile/src/journeys/kotlin/…/Journeys.kt`
(added to both modules), so the profile is generated by the flows that are measured.

| # | Journey | What it does |
|---|---|---|
| 1 | Startup | cold start, wait until a card below the hero has focus (= first poster row drawn) |
| 2 | Home scroll | LEFT ×10 along the first row, DOWN ×3, RIGHT ×5 |
| 3 | Open details | OK on a poster (steps down first if the focused card is a wide "continue watching" one), wait, Back |
| 4 | Browse grid | UP to the top bar, «فیلم» tab, OK, DOWN ×6 in the grid, Back |

| Module | Plugin | Contents |
|---|---|---|
| `:baselineprofile` | `com.android.test` + `androidx.baselineprofile` | `BaselineProfileGenerator`: `startup()` (journey 1, `includeInStartupProfile = true`, so `startup-prof.txt` holds only startup) and `allJourneys()` (1-4, into `baseline-prof.txt`) |
| `:benchmark` | `com.android.test` | `StartupBenchmark` (`StartupTimingMetric`), `HomeScrollBenchmark` (`FrameTimingMetric`), `OpenDetailsBenchmark` (`TraceSectionMetric("details_ready")` + `FrameTimingMetric`). COLD, 5 iterations; each has a `…WithoutProfile` (`CompilationMode.None`) and a `…WithProfile` (`Partial(BaselineProfileMode.Require)`) test |

`:app` applies `androidx.baselineprofile` and consumes `:baselineprofile`; the plugin adds the `nonMinifiedRelease`
and `benchmarkRelease` variants. The `:benchmark` module's `benchmark` build type falls back to `:app`'s **`release`**
variant (R8 on, debug-signed, `<profileable>`), i.e. the exact APK that is sideloaded.

### 1. Generate the profile on the `TV_API34` emulator
AGP 9.4.1 cannot do this with a Gradle Managed Device: `ManagedVirtualDevice.systemImageSource` accepts only
`aosp`, `aosp-atd`, `google` and `google-atd` (no `android-tv`/`google-tv` images). So the generator runs on the
connected emulator. The emulator needs working internet (the first run loads the real home feed).
```bash
tools/tv.sh emu TV_API34                  # start the AVD, wait for boot
adb devices                               # note the serial, e.g. emulator-5554
# ANDROID_SERIAL is required whenever the real TV is connected too: Gradle's connected tasks use ALL devices.
ANDROID_SERIAL=emulator-5554 tools/gw.sh :app:generateBaselineProfile
```
It builds `:app` `nonMinifiedRelease` and the generator APK, installs both, runs `BaselineProfileGenerator`
(several minutes: each test repeats its journey until the profile is stable, at most 15 times) and copies the result into
`app/src/main/generated/baselineProfiles/` (`baseline-prof.txt`, `startup-prof.txt`). **Commit those two files.**
Every release build then packages the profile (`assets/dexopt/baseline.prof`) and R8 uses the startup profile for
dex layout. Check with `tools/gw.sh :app:assembleRelease && unzip -l app/build/outputs/apk/release/app-release.apk | grep baseline.prof`.

Without the plugin task (profile files then stay in `baselineprofile/build/outputs/…/connected_android_test_additional_output`,
copy them by hand):
```bash
ANDROID_SERIAL=emulator-5554 tools/gw.sh :baselineprofile:connectedNonMinifiedReleaseAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.androidx.benchmark.enabledRules=baselineprofile
```
Regenerate after big UI changes (new screens, navigation, a library bump).

### 2. Measure on the real TV (profile gain and budgets)
```bash
tools/tv.sh connect <tv-ip>               # once; accept the prompt on the TV
export TV_SERIAL=<tv-ip>:5555
adb -s "$TV_SERIAL" shell setprop persist.traced.enable 1     # Android 10: Perfetto for the trace metrics, after each reboot
ANDROID_SERIAL="$TV_SERIAL" tools/gw.sh :benchmark:connectedBenchmarkAndroidTest
# one class: add  -Pandroid.testInstrumentationRunnerArguments.class=app.bolbol.tv.benchmark.StartupBenchmark
```
This builds `:app` `release` and the benchmark APK, installs both on the TV (same package and debug key, app data
is kept) and runs the 6 tests (5 iterations each; expect 10-20 min). Results: the console summary, plus JSON and `.perfetto-trace`
files (`find benchmark/build/outputs -name '*benchmarkData.json' -o -name '*.perfetto-trace'`; open traces in
ui.perfetto.dev). Read:
- `StartupBenchmark`: `timeToInitialDisplayMs` median, `…WithoutProfile` vs `…WithProfile` = the profile's gain; budget 1.5 s.
- `HomeScrollBenchmark`: `frameDurationCpuMs` P90 (budget 16 ms) and `frameCount`. `frameOverrunMs` is absent on API 29.
- `OpenDetailsBenchmark`: `details_readyMs` (budget 0.4 s cached / 1.0 s network), once the UI emits the section.

If a run fails:
- `ERRORS (not suppressed): EMULATOR`: benchmarks must not run on an emulator (numbers are meaningless). For a smoke
  test only, add `-Pandroid.testInstrumentationRunnerArguments.androidx.benchmark.suppressErrors=EMULATOR`.
- `LOW-BATTERY` (a TV has no battery): add `…suppressErrors=LOW-BATTERY` the same way.
- `BaselineProfileMode.Require` fails: the APK has no profile. Do step 1 first, then rebuild.
- "Home rows were not drawn within 30 s": the TV is offline or the feed is unreachable.

### UI hooks the journeys can use (optional; nothing fails while they are missing)
The app has no resource ids, so the journeys wait on "a card below the hero has focus" plus bounded idle waits.
These hooks make them exact. They are not added yet (feature/app code is owned elsewhere):
1. Root composable (`MainActivity` `setContent`): `Modifier.semantics { testTagsAsResourceId = true }`, so test tags show up
   as resource ids for UiAutomator.
2. `Modifier.testTag("details_screen")` on the details root: the journey then waits for it instead of sleeping 2 s.
3. **`trace("details_ready") { … }`** (`androidx.tracing`) from the OK press until the details content is first drawn
   (use `Trace.beginAsyncSection` / `endAsyncSection` with the same name if that spans threads). Required for the
   `details_ready` metric; until then `OpenDetailsBenchmark` reports frame metrics only.
4. `reportFullyDrawn()` (or `ReportDrawn` from `androidx.activity.compose`) when the first home row is drawn: adds
   `timeToFullDisplayMs` to `StartupTimingMetric` (may still be missing on API 29; TTID is the fallback).

## Standing performance rules
- Images: Coil 3, always sized to the composable (posters ~ 200×300 dp, backdrops ≤ 1280×720),
  hardware bitmaps, RGB_565 for posters is acceptable, memory cache ≤ 15 % of heap.
- Backdrop changes on focus are **debounced (~300 ms)** and crossfade once. No autoplay video.
- Lazy lists: stable `key`, `contentType`, no heavy work in item composition; focus scale via `graphicsLayer`.
- Network: OkHttp disk cache (50 MB) + Room cache of home rows; stale-while-revalidate.
- Player: one ExoPlayer at a time, released on exit; `DefaultLoadControl` ≈ 30–50 s buffer,
  60 MB byte cap, 1.5 s to start / 3 s after rebuffer (tune with data); SurfaceView only.
- Release builds only for measurement: R8 full mode, `debuggable=false`, profile installed.
