# v1.1-2 · Quality-switch stall (720p → 1080p)

**User report (real TV):** "sometimes there is a big lag when choosing a higher quality; going lower and then back up makes it better."
**Goal:** a 720p → 1080p switch shows a picture within ~3 s on the TV.
**Status:** fixed in code from evidence (dev-machine network probes + code reading). **Not yet measured on the TV** (no ADB at the time). See "How to measure on the TV" below.

## 1. Network facts (dev machine, 2026-10-11, small range requests only)

Probed with `curl` against `post/player-links` of a movie (The Naked Gun 2025, postId 353371) and a series episode
(Kill Jackie S01E01, postId 623954). Each file got one 2-byte range request (timing, size, range support) and one
64 KB range request (box order); no file was downloaded.

| File | Host | Size | HTTP | `moov` | DNS / connect / TLS / first byte (s) |
|---|---|---|---|---|---|
| movie 1080p | `dl20.acenteri.ir` (nginx cache → backend, `X-Cache-Status: MISS (Backend)`) | 2.60 GB | 1.1 | **front, 3.65 MB** | 0.07 / 0.16 / 0.26 / 0.37 |
| movie 720p | **`dl2.ecenteri.ir`** (nginx) | 0.84 GB | 1.1 | front, 4.46 MB | **1.69** (cold DNS) / 1.79 / 1.91 / 2.12, warm: 0.003 / 0.10 / 0.22 / 0.34 |
| movie 480p | `dl20.acenteri.ir` | 0.42 GB | 1.1 | front, 3.79 MB | 0.003 / 0.10 / 0.22 / 0.34 |
| episode 1080p / 720p / 480p | `dl1.hostikadeh.ir` (IIS 10) | 1.16 / 0.49 / 0.24 GB | **2** | front, ~2.0 MB each | 0.003 / 0.09 / 0.29 / 0.38-0.41 |

- **Different qualities are on different hosts for movies** (1080p + 480p on `dl20.acenteri.ir`, 720p on `dl2.ecenteri.ir`).
  Series qualities share one host. So 720p → 1080p on a movie means a new DNS lookup + TCP + TLS to a host the TV
  hasn't talked to. A cold DNS lookup took 1.7 s here. **"Lower, then back up" fixes it because 480p lives on the
  1080p host**: the detour warms DNS, the TLS session and the edge cache for 1080p.
- DNS TTLs are 75-120 s, and nginx drops idle keep-alive connections after about a minute, so a warm-up only helps
  for a minute or two.
- `Accept-Ranges: bytes` and `206` everywhere. Mid-file ranges (1.3 GB and 1.9 GB into the 1080p file) answer as fast as
  offset 0 (~0.1 s server time), so seeking is not slow at the CDN.
- `moov` is at the **front** of every file (no tail request needed), but it is **2-4.5 MB**. ExoPlayer must download and
  parse all of it before the first frame, on every switch (it's a different file).
- ExoPlayer's first request has **no Range header** → `200 OK`, `Content-Length` 2.6 GB, `Last-Modified` + `ETag`,
  no `Cache-Control`. OkHttp treats that as cacheable.
- Keyframes (from `stss` of the episode files): 25 fps, a keyframe every 25-250 frames (**1-10 s**, mean ~3 s); the
  movies are x264 (Pahe) with the same 250-frame cap.
- Movie hosts speak HTTP/1.1: after the `moov`, ExoPlayer closes the open-ended request (that connection can't be
  reused) and opens a second, ranged one at the start position, so a cold switch needs two TCP+TLS handshakes.

## 2. Code path before the fix

`PlaybackController.switchStream` → `setMediaItem(new, oldPosition)` + `prepare()`:
1. GET without Range on the new host (DNS + TCP + TLS if cold) → download + parse the 2-4.5 MB `moov`.
2. Range GET at the **keyframe before** the old position (a new connection on HTTP/1.1 hosts).
3. Decode-but-don't-show every frame from that keyframe up to the old position (up to 250 frames at 1080p),
   because `setMediaItem(item, position)` **ignores `SeekParameters`** (checked in Media3 1.11.1 bytecode:
   `MediaPeriodHolder.handlePrepared` takes the start position from `selectTracks`; nothing applies seek parameters).
   Worst case that is ~5 MB extra download plus a few seconds of hidden decoding.
4. Then `bufferForPlaybackMs` (1.5 s) before READY.

Contributing factors:
- Media used the **shared API client**: 50 MB disk cache (each open-ended 200 is teed to disk, then up to 100 ms is
  spent on close trying to complete the entry, which is then discarded), **connect 10 s / read 20 s** timeouts. A
  connection that stalls mid-switch hangs for 20 s before Media3 retries on a fresh one.
- Media3's default retry delays (0, 1, 2, 3 … s; 404/403 retried 3 times before the error panel).
- No watchdog: a stalled switch showed a frozen frame + spinner until the timeouts and retries ran out.
- `VideoLayers.kt` has **no shutter**: a plain `SurfaceView`, nothing in our UI paints black during a switch. The
  last frame stays (SurfaceFlinger keeps the last buffer when the codec is released); the UI only adds the buffering
  spinner. If the TV turns out to show black, it comes from the MTK codec release, not our Compose code.
- LoadControl: 40 s max buffer ≈ 20 MB at 1080p (~4 Mbit/s), well under the 60 MB cap. **Not changed**: nothing points at it.

## 3. What changed (each piece is small and logged)

| Change | Where | Why / expected gain |
|---|---|---|
| **Keyframe start for switches**: items built by `switchStream` are tagged `KeyframeStart`; a wrapping `MediaPeriod` moves the *first* track selection to `SeekParameters.PREVIOUS_SYNC` (≤ 15 s back, else unchanged). Later seeks keep the normal mode. | `KeyframeStart.kt` (+ `KeyframeSnap` pure rule) | No hidden decode of up to 250 frames, no extra MBs. Viewer sees ≤ 10 s (mean ~1.5 s) replayed, never skipped. |
| **Media client**: `MediaHttp.mediaClient(shared)` = `newBuilder()` (same pool/dispatcher/DNS) with **no disk cache**, **connect 6 s / read 10 s**. Subtitles keep the cached client. | `MediaHttp.kt`, `PlayerFactory` | No disk tee of video; a stalled connection fails in 10 s and the retry gets a fresh one. |
| **Fast retries**: `MediaLoadErrorPolicy` = Media3 default with delays 0.2 / 0.5 / 1 / 2 s, and **4xx (except 408/429) fatal**. | `MediaHttp.kt` (`MediaRetry` pure) | Errors reach the panel («کیفیت پایین‌تر») sooner; transient ones retry sooner. |
| **Watchdog**: no first frame 8 s after a switch and no bytes for 2 s → drop idle connections and re-prepare once; stalled again (or 20 s total) → error panel. While bytes still arrive it waits (a slow 1080p `moov` is not a failure). | `StreamSwitchPolicy` (pure) + controller | Worst case ≤ 20 s instead of "until timeouts run out", and usually 8-10 s with a fresh connection. |
| **Pre-warm**: after the first frame of `start()`, one `Range: bytes=0-0` request per *other* host of the title's streams (async on OkHttp's dispatcher; ≤ 1 per host per minute). `controller.prewarmOtherStreams()` is public for the picker. | `ConnectionPrewarmer` (+ `PrewarmPlan` pure) | DNS + TCP + TLS (0.35-2 s) paid before the viewer chooses. Movies: 1 request; series: 0. |
| **`switchingQuality: StateFlow<Boolean>`**: true from the switch until first frame/READY. | controller | UI keeps the last frame with «در حال تغییر کیفیت…» instead of a bare spinner. |
| `QualitySwitchIndicator` composable (pill: small accent spinner + label). | `feature/playback/…/QualitySwitchIndicator.kt` (new) | Manager wires it into `PlayerScreen`. |
| **Logs**: `BolbolPerf stream_switch=…ms` kept; new `BolbolSwitch` breakdown + overlay line `swtch`. | controller, `PlaybackDiagnostics` | Measure on the TV. |

## 4. How to measure on the TV

1. Install the build and start logcat on the dev machine:
   ```bash
   tools/tv.sh connect <tv-ip>
   tools/tv.sh install
   adb logcat -c && adb logcat -s BolbolPerf:I BolbolSwitch:I BolbolPlayer:W
   ```
2. On the TV: open a **movie** (e.g. The Naked Gun 2025), play at 720p, wait ~1 minute, then open the settings panel and pick 1080p. Repeat 3×
   at different points; then the same with a series episode (one host). Optionally turn on the overlay (DPAD_UP ×3):
   the `swtch` line shows the last switch.
3. Expected lines:
   ```
   BolbolSwitch: prewarm host=dl20.acenteri.ir http=206 in 380ms
   BolbolPerf  : stream_switch=2610ms stream=1080p/SUBTITLED
   BolbolSwitch: switch 720p/SUBTITLED->1080p/SUBTITLED host=dl20.acenteri.ir result=ok firstByte=412ms moov=1830ms rangeByte=2200ms firstFrame=2610ms ready=3900ms snap=-1.6s requests=2 mb=4.9 errors=0 reprepares=0
   ```
   Read it as: `firstByte` = DNS+TCP+TLS+server (should be ~0.4 s when pre-warmed, 0.4-2 s cold); `moov` = `moov`
   downloaded and parsed (≈ size ÷ Wi-Fi throughput + parse); `rangeByte` = the ranged request at the start position
   answered; `firstFrame` = picture on screen (**goal ≤ 3000 ms**); `snap` = how far back the keyframe start went.
   `result=` is `ok`, `gave_up` (watchdog → error panel), `error_NETWORK`…, `replaced`, `stopped` or `released`.
   `reprepares=1` / `errors>0` mean a stall happened; a line `no first frame, no bytes …: re-preparing` precedes it.
4. If `moov` dominates (> 2 s), the remaining lever is the Wi-Fi throughput to Iran (the `moov` must be read on every
   switch). Options for later: cache each quality's `moov` bytes after the first play (disk), or start the switch
   from the old stream's frame while the new one loads in a second player (costs RAM; not on a 2 GB TV).

## 5. Open points
- Unmeasured on the TV (rule 1): numbers above are dev-machine network facts plus expectations.
- `start()` (first play / resume) could use the same keyframe start for a faster resume TTFF; left unchanged on purpose
  (out of scope; resume position would move back ≤ 10 s).
- The pre-warm is most useful right before a choice: wire `controller.prewarmOtherStreams()` to the quality/audio
  picker opening (throttled to one tiny request per host per minute).
